Anatomy of a harness

A model turns text into text. That is all it does. Everything that makes it an agent — what it sees on each call, where its commands run, how it splits up work and when it stops to ask a person — is the harness. Here the harness is drawn as a machine running one ordinary task. Press play to watch it work, then pull parts out and run it again.

    01If you’re not the model, you’re the harness

    A harness is every piece of code, configuration and execution logic around a model that is not the model itself. The model is the engine in the middle of the figure: it is sealed, it takes text in through one slot and puts text out of another, and it remembers nothing between calls. Each call re-reads the whole tray in front of it — the context window — from the start.

    That last fact explains most of the machine. The window has a fixed size, here 200,000 tokens, and every token in it is sent again on every call, so a 40k-token log that lands in the window early is paid for once for each call that follows. The meter under the figure, tokens billed, adds up exactly that: the size of the window at each model call.

    The parts on the board below come from a sketch of the four jobs a harness does. LangChain’s The Anatomy of an Agent Harness (Vivek Trivedy, March 2026) and its agents documentation use the same split.

    02Context management

    Decide what the model sees on each call, inside a window that never grows.

    Skills (1) are a rack of playbook cards. The window holds only each card’s name and a one-line description, about 120 tokens a card; when the task matches one, the full card is pulled in. This is progressive disclosure: knowledge is available without being paid for until it is used. Take the rack away and all eight playbooks have to sit in the system prompt from the first call.

    Memory (2) is the filing cabinet: an AGENTS.md file and notes saved by earlier sessions, loaded at the start. It is small, but it is the reason the agent knows that this repository runs its tests in UTC. Without it, the first fix is wrong.

    Summarization (3) is the press. When the tray passes 160k tokens, it keeps the pinned instructions and presses everything else into one short summary, so the run can carry on. In the full harness it never moves, because the other parts keep the tray small. It earns its place when they fail: remove subagents and offloading and the press is the only thing between the run and a full window.

    Context offloading (4) is the chute. A test log can be 40,000 tokens of stack traces; the model needs maybe twenty lines of it. The chute writes the full output to a file and leaves a short head, tail and path in the tray. Nothing is lost — the agent can read the file if it needs more — but nothing is paid for twice.

    03Execution environment

    Give the model a computer: somewhere to run things and somewhere to keep files.

    The REPL (5) — read, execute, print, loop — is the terminal. The agent writes a command, the harness runs it, and the output becomes the next input. This loop is how an agent checks its own work. Without it the agent can only read code and guess, and every change it makes goes out untested.

    The sandbox (6) is the glass case around the terminal and the shelves: a disposable machine with only the repository mounted, no personal credentials, and a network allowlist. In this run nothing malicious happens, but the agent does run npm ci, which executes the install scripts of hundreds of packages. Remove the case and those scripts run on your own machine, as you.

    The file system (7) is the shelving: a scratch shelf for work in progress and a persistent shelf for what should outlast the session. Several other parts stand on it — offloading writes to it, memory reads from it, scratch scripts live on it — so removing it takes them out too.

    Write & run code (8) is the workbench. Instead of only calling fixed tools, the agent writes a twelve-line script that builds one order at 23:30 UTC and prints its delivery date. The script prints the wrong day, and the bug is found with 500 tokens of output instead of another full test log.

    04Delegation

    Split work that is too big for one window, and keep track of where the run is.

    Planning (9) is the peg board. The agent’s first act is to write five to-dos, and it ticks them off as it goes. It sounds like bookkeeping, but it changes behaviour: with a list to check, the agent runs the full suite before it calls the job done. Without one, it stops at the first green test.

    Subagents (10) are the two small engines behind the model. Each has its own small window. The explorer reads the fourteen files around checkout — 110,000 tokens — in its window and hands back a 1,800-token report. The main window never sees the files. The explorer’s own two calls still cost about 116,000 tokens, and the meter counts them; but they are paid once, where the main agent would have re-sent those files on every call that followed. Subagents do not make reading free. They make it happen once, somewhere else, and that is the single biggest saving in the run.

    05Steering

    Put a person at the decisions that should not be automatic.

    Human in the loop (11) is the gate across the output belt. Most of a run should not need anyone. A push, a payment, a deletion or an email to a customer should. At the gate the run pauses; a person approves, edits or rejects the action, and the run continues. Here the person approves the pull request but changes its target from main to a branch. Without the gate, the change lands on main unread.

    A gate costs nothing in tokens. Its cost is a person’s attention, which is why it belongs at a few high-impact actions rather than every step.

    06Every part, pulled out one at a time

    Each row is the same task run with one part removed and everything else installed. Removing a part also removes the parts that stand on it, shown in the second column. Click a row to load that machine.

    Two things stand out. The parts that save the most tokens — subagents, offloading, skills — are the ones that keep large text out of the window, not the ones that shrink it after the fact. And the parts that cost few or no tokens — the sandbox, the gate, planning — are the ones that stop a run from doing the wrong thing. A harness is judged on both.

    07What the figure leaves out

    • The numbers are illustrative. Token sizes are chosen to match common orders of magnitude for a coding agent; they are not measurements of any product. The run is scripted, not a live model. The arithmetic — what is in the window at each call, and what that adds up to — is exact for the script.
    • One path through the task. A real agent branches, retries and sometimes recovers on its own. Here each missing part has one fixed consequence.
    • Prompt caching is not modelled. Providers discount a repeated prefix of the window, which lowers the cost of carrying stable instructions. It does not shrink the window, and tool output added mid-run is rarely cached.
    • More parts exist. Real harnesses also have the system prompt, tool definitions and MCP servers, hooks and middleware (lint checks, continuation), model routing and handoffs. The board shows the four jobs; it is not a complete parts list.
    • Steering is more than a gate. A person can also interrupt and redirect a run mid-way. The figure shows only approval before an action.
